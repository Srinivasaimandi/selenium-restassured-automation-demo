Selenium Automation Demo

A practical guide to how this Java framework configures environments, starts the app under test, runs browser and API tests, manages test data, validates API responses, and organizes its source files. It is a port of the Playwright framework in copilot-playwright-framework: the same scenarios, test data, and safety rules, rebuilt on a Java stack.

Selenium 4 + WebDriver BiDi Java 21 TestNG 7 REST Assured REST · GraphQL · OpenAPI JSON Schema validation axe-core accessibility Allure reports

Overview

The framework tests the Users App at the BASE_URL selected for a run. Browser tests cover the home page, login flow, users screen, accessibility, network-failure states, and complete user journeys. API tests cover the REST endpoints, the GraphQL API, and the published OpenAPI document, and validate every response body against a JSON Schema.

UI tests

Located in com.demo.tests.ui and tests.ui.e2e; run in Chrome by default, with Firefox and Safari supported. Includes axe scans and BiDi network mocks for API failures, slow responses, and row actions.

API tests

Located in com.demo.tests.api; REST Assured, no browser. Covers REST, GraphQL, and the published OpenAPI contract. The data reset in tests.api.destructive runs last, in its own suite section.

Shared code

Page objects, base test classes, TestNG listeners, test data, API clients, JSON Schemas, and environment checks are kept in focused packages.

The Users App is included in app/ as a Git submodule. For loopback targets under TEST_ENV=local or TEST_ENV=test, the suite starts it with npm --prefix app start (running npm ci --prefix app first if app/node_modules is missing), waits up to 120 s for BASE_URL to respond, and stops it when the suite ends. Remote test, development, and staging targets must already be reachable.

The app is not updated automatically on local runs. The suite tests whatever commit app/ is checked out at, and reuses an app that is already responding at BASE_URL. To test the latest app code, run git submodule update --remote --init app first. CI does this on every run. Fix app defects upstream in users-app-demo, not in app/.

Quick start

  1. Install JDK 21+, Maven 3.9+, Node.js 22 (runs the app under test), and Chrome.
  2. Clone with submodules so app/ is checked out.
  3. Copy an environment example and set the login credentials.
  4. Run mvn test; the suite starts the bundled app for loopback targets.
git clone --recurse-submodules <this repo>
cd selenium-automation-demo
cp env/.env.example env/.env.local   # then fill in LOGIN_USERNAME and LOGIN_PASSWORD
mvn test

Selenium Manager downloads a matching chromedriver on first use, so the first run is slower. Don't keep an old chromedriver on your PATH: Selenium uses it instead of downloading one, and a version that doesn't match your Chrome fails with DevToolsActivePort file doesn't exist.

For API tests that create or delete users, use a loopback URL with TEST_ENV=local or a dedicated, disposable TEST_ENV=test target with an explicit hostname allowlist.

How a test run works

  1. Alter suite.
    BrowserParallelism runs the ui section one test at a time when the browser allows only one session (Safari).
  2. Select environment.
    TEST_ENV chooses the matching env/.env.* file; an unknown value fails fast.
  3. Resolve URL.
    BASE_URL is required except for the local default http://127.0.0.1:9899.
  4. Start local app.
    SuiteLifecycle starts app/ for loopback targets, or reuses a responding server. Its log goes to target/app-server.log.
  5. Authenticate once.
    The setup section logs in through the UI and saves the x-api-token for the UI tests.
  6. Run sections.
    api and ui run in parallel threads; api-destructive runs last and skips after any failure.
  7. Per-test resources.
    Each UI test gets a fresh browser; each test gets its own logged-in API clients on first use.
  8. Capture diagnostics.
    Failed UI tests attach a screenshot and the page source; API calls are attached as request/response pairs.
  9. Stop app.
    The app the suite started is stopped, including npm's child node process.

testng.xml defines the sections and listeners; pom.xml configures Surefire, Allure, AspectJ (for Allure @Step), and Spotless. In CI, failed tests are retried twice; locally there are no retries unless -Dretries=N is set.

Base classes and lifecycles

Playwright fixtures become methods on two abstract base classes. Resources are held in ThreadLocals, because TestNG runs methods of one instance in parallel.

API resources (BaseTest)

  • usersApi() logs in with POST /api/login on first use and returns a UsersApiClient with its own API key.
  • graphqlApi() authenticates the same way and sends queries and mutations to /graphql.
  • createApiTestUser() checks the target is safe to change, creates a uniquely named user, and returns an ApiTestUser that deletes it on close().
  • TestData provides shared, read-only reference values as constants.

Defined in BaseTest.java. Clients are lazy: nothing logs in unless a test asks for a client, and each test gets its own key, so a test can log out without affecting others. Clients are released after every method.

UI resources (BaseUiTest)

  • A new browser session is created before every test method and quit after it.
  • loginPage() and usersPage() return page objects bound to the test's driver.
  • expect() returns waiting assertions: visible, hidden, count, texts, text, value, enabled, focused, attribute, urlMatches, title, and a generic poll.
  • openAuthenticatedUsersPage() writes the shared token into localStorage and opens the users screen signed in. Tests start signed out otherwise.
  • usersApiMock() mocks users-API endpoints with WebDriver BiDi request interception: canned responses, network failures, and requests held back to test slow responses.
  • axe() returns an axe-core AxeBuilder preconfigured with the WCAG 2.1 A/AA tags (wcag2a, wcag2aa, wcag21a, wcag21aa).

BaseUiTest extends BaseTest, so UI tests can also use the API clients. When the setup test did not run (for example, a single class run on its own), AuthState logs in through the API once instead. Authenticated tests are skipped when credentials are not configured.

API client and response validation

UsersApiClient centralizes authenticated requests for login, logout, list, search, count, create, bulk create, retrieve, update, delete, and data reset. Its successful JSON responses pass through ApiResponses.parse, which checks the status, validates the body against a schema, and maps it to a record. Most operations also have a …Response variant that returns the raw REST Assured response for negative tests.

Runtime contracts are JSON Schema files in src/test/resources/schemas/ (named in Schemas): API key, error, message, individual user, user list, user count, and the GraphQL response envelope. A response with an unexpected status, invalid JSON, or an invalid shape fails with the body in the message. The shared Jackson mapper ignores unmodeled fields, so ApiUser never reads the password.

ApiSpecs builds every request: base URI, JSON content type, the x-api-key header, and the AllureRestAssured filter that attaches each call to the report.

GraphqlClient holds a document for every query and mutation in the app's GraphQL schema; UsersGraphqlTest covers them, including cross-checks against the REST API and the unauthenticated error.

OpenApiContractTest reads the OpenAPI document that Swagger UI embeds in /api-docs/swagger-ui-init.js (OpenApiDocument). It checks that the documented operations exactly match UsersApiClient.OPERATIONS, that login needs no API key, that the API-key header matches, and that every documented JSON response schema agrees with the test's schema file.

Tests for behaviour the app does not implement yet are annotated @KnownDefect("…") and put in the known-defect group. They are reported as passing while they fail, and fail once the app is fixed, as a reminder to remove the annotation. Current defects: the OpenAPI document omits 204 for GET /users and GET /users/search and 403 for DELETE /users/{id}; and the protected-user lock icon puts aria-label on a role-less <span> (axe aria-prohibited-attr).

Data reset: PUT /users/reset-data deletes every user added since startup, including users other tests are using. Only ResetDataTest in tests/api/destructive/ calls it, in the api-destructive section, which runs after every other section and is skipped if any earlier test failed. UI tests always mock the reset.

Test data and safety rules

  • TestData holds the seeded user Jane, the delete-protected user ID, a missing ID, search terms, and mock users.
  • NewUser.unique() generates collision-resistant users (UUID-based name, email, and username) for CRUD tests.
  • TestData.MockUsers have IDs far above the seeded ones (901, 902), so a request that escapes its mock changes no real record.
  • Environment reads settings and credentials and guards mutation targets.
  • The test-data group marks tests that create or delete application records.

createApiTestUser() and ResetDataTest call Environment.assertTestDataTargetIsSafe(), which allows only loopback hosts under TEST_ENV=local, or hostnames listed in TEST_DATA_ALLOWED_HOSTS under TEST_ENV=test. Anywhere else they fail before sending a request. Leave them out of shared environments with -Dexclude.groups=test-data. Do not configure a production host as a test-data target.

Browser support

Selenium Manager downloads a matching driver, so no driver setup is needed. Network mocks (UsersApiMock) and the smoke test's console and network checks (BrowserDiagnostics) use WebDriver BiDi, enabled with the webSocketUrl capability. Safari doesn't support BiDi yet.

On Safari, BiDi-dependent tests are reported as skipped with the reason, and the ui section switches to one test at a time automatically. Enable Safari automation once: run safaridriver --enable, then turn on Develop › Allow Remote Automation.

Reports

  • Allure results are written to target/allure-results; mvn allure:serve or mvn allure:report renders them.
  • Tests carry Allure @Feature and @Story labels; page-object and client actions are reported as @Steps (woven by the AspectJ agent configured in Surefire).
  • Failed UI tests attach a screenshot and the page source. Every REST Assured call is attached as a request and response pair.
  • The Allure plugin keeps trend history between runs in .allure/ (Git-ignored). CI keeps it in the Actions cache for branch runs, so pull requests don't mix into the trend.
  • Plain TestNG/Surefire results are in target/surefire-reports; the local app's log is target/app-server.log.

Adding tests

UI test

  1. Add a class under com.demo.tests.ui, or a full user journey under com.demo.tests.ui.e2e, extending BaseUiTest.
  2. Use page-object By fields. Prefer ids, then accessible names (aria-label, visible text).
  3. Assert on the page through expect(), which waits; don't assert on a single findElement read, and don't add fixed sleeps.
  4. Call openAuthenticatedUsersPage() to start signed in, or use loginPage() when testing login itself.
@Test(groups = "users", description = "filters users by email without case sensitivity")
public void filtersByEmailIgnoringCase() {
  UsersPage usersPage = openAuthenticatedUsersPage();

  usersPage.searchFor(TestData.Searches.JANE_BY_EMAIL_CASE_INSENSITIVE);

  expect().visible(usersPage.userRow(TestData.JANE.name()).locator());
  expect().count(usersPage.userRows, 1);
}

API test

  1. Add a class under com.demo.tests.api extending BaseTest.
  2. Use usersApi() so requests are authenticated and response schemas are validated.
  3. Use createApiTestUser() in try-with-resources only for tests that need a record created for the test.
  4. Use graphqlApi() for GraphQL; add new operations to GraphqlClient.Documents.
  5. When the client calls a new REST operation, add it to UsersApiClient.OPERATIONS so the contract test checks it, and add a schema file for its response.
  6. Put data-changing tests in the test-data group.
@Test(
    groups = {"api", "test-data"},
    description = "GET /users/{id} returns a created user")
public void getReturnsCreatedUser() {
  try (ApiTestUser created = createApiTestUser()) {
    ApiUser user = usersApi().getUser(created.id());

    assertThat(user)
        .isEqualTo(new ApiUser(created.id(), created.name(), created.email(), created.username()));
  }
}

Accessibility, mocked, and known-defect tests

  • Accessibility: run axe().analyze(driver()) and assert there are no violations. Scope with .include(...) instead of disabling rules.
  • Network failures: use usersApiMock().fulfill, respondWithUsers, abort, or hold. The newest mock wins, and unmatched requests reach the real app. Use TestData.MockUsers for rows a test edits or deletes, and always mock data resets in UI tests. Put these tests in the mocked group.
  • To check what the page sent, use FetchRecorder.install(driver()); BiDi in Selenium does not expose request bodies yet.
  • Known app defects: write the test for the correct behaviour, annotate it with @KnownDefect("…") describing the defect, and add the known-defect group.
@Test(
    groups = {"users", "mocked"},
    description = "shows a fetch error when the users request fails at the network level")
public void networkFailureOnList() {
  UsersPage usersPage = openAuthenticatedUsersPage();
  expect().visible(usersPage.userRow(TestData.JANE.name()).locator());
  usersApiMock().abort(Endpoint.LIST, "GET");

  usersPage.refreshUsers();

  expect().visible(usersPage.fetchFailedMessage);
}

Run mvn spotless:apply before committing; CI fails on unformatted code.

Continuous integration

The GitHub Actions workflow (selenium.yml) runs on every push, on pull requests, and on manual dispatch. It uses Java 21 (Temurin) and Node.js 22 on ubuntu-24.04 with a 30-minute timeout, and cancels an in-progress run for the same ref. It runs these steps in order:

  1. Check out the repository with submodules, then run git submodule update --remote --init app so the app is tested at the latest main commit (logged in the job output).
  2. Set up Java and Node with Maven and npm caches; fail early if the credential secrets are missing.
  3. Install app dependencies with npm ci --prefix app, then check formatting with mvn spotless:check.
  4. Restore Allure history from the Actions cache.
  5. Run mvn test against http://127.0.0.1:9899 in the runner's preinstalled Chrome, with two retries.
  6. Build the Allure report; on non-PR runs, save Allure history to the cache.
  7. Upload the Allure report, Surefire results, and target/app-server.log as the test-results artifact.
